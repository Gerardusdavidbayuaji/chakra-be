# Midtrans Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** User bisa membayar cicilan lewat Midtrans Snap, webhook menerapkan pembayaran lewat aturan domain yang sama dengan pembayaran manual, setiap pembayaran sukses dinotifikasi ke Telegram, dan dana yang tidak bisa diterapkan ditampung untuk dialokasikan atau di-refund manual oleh admin.

**Architecture:** Entity baru `PaymentTransaction` (satu baris per `order_id`) memegang semua transisi status pembayaran. `Premi.CheckCanPay` menjadi satu-satunya sumber aturan "boleh dibayar", dipakai oleh pembuatan link, webhook, dan `MarkInstallmentPaid`. Efek samping (notifikasi, permintaan expire) berjalan lewat domain event yang di-dispatch sebelum commit, sehingga tersimpan dalam transaksi yang sama. Pemanggilan Midtrans di luar request (expire) dilakukan `PaymentExpiryProcessor`.

**Tech Stack:** .NET 9, EF Core 9.0.1 + Npgsql 9.0.2, MediatR 14.1.0, FluentValidation 12.1.1, Mapster 10.0.0-pre02, Gridify 2.20.0, typed `HttpClient`.

**Spec:** `docs/superpowers/specs/2026-11-22-midtrans-design.md`

## Global Constraints

- **Jangan menjalankan `git commit`, `dotnet build`, `dotnet run`, `dotnet test`, maupun `dotnet ef`.** User menjalankannya sendiri. Langkah verifikasi di plan ini ditujukan untuk user.
- Repo belum punya project test. Pembuktian dilakukan lewat build per task dan skenario sandbox di Task 8.
- `CreatedAt`/`UpdatedAt` tidak di-set manual (interceptor). Id baru memakai `XxxId.New()`. Waktu dari `TimeProvider`, bukan `DateTime.UtcNow`.
- Pesan error API berbahasa Inggris. Teks Telegram berbahasa Indonesia.
- Style kode mengikuti codebase: constructor klasik, field `_camelCase`, file-scoped namespace, `Result<T>` + `ApiResponse`/`ApiErrorResponse`, `ToErrorResult()` di endpoint.
- Event handler domain **tidak boleh** memanggil API eksternal (aturan di `DispatchDomainEventsInterceptor`).
- `Chakra.Application` tidak mereferensikan Npgsql. Pelanggaran unique index ditangkap sebagai `DbUpdateException` (bukan `DbUpdateConcurrencyException`).
- Semua parsing/format angka dari/ke Midtrans memakai `CultureInfo.InvariantCulture`. Format rupiah untuk teks Telegram memakai `ToString("N0", CultureInfo.GetCultureInfo("id-ID"))` → `1.714.285`.
- `order_id` = `"CHK-" + Guid.CreateVersion7().ToString("N")`.
- Default settings: `IsProduction = false`, `PaymentExpiryHours = 24`, `ExpiryProcessorIntervalSeconds = 60`.

## Review Focus

1. **Locale mesin `id-ID` saat parsing `gross_amount`.** `"1714285.00"` harus terbaca 1.714.285, bukan 171.428.500. Parsing di Task 5 memakai `decimal.Parse(value, NumberStyles.Number, CultureInfo.InvariantCulture)`; dicek di Task 8 skenario 1 (cicilan jadi `Paid`, bukan `Unapplied(AmountMismatch)`).
2. **Signature dihitung dari string mentah `gross_amount` di body notifikasi**, bukan dari angka yang diformat ulang. Kalau diformat ulang, semua notifikasi asli ditolak 401. Task 5 Step 1; dicek di Task 8 skenario 1 dan 5.
3. **Settlement datang untuk transaksi yang sudah kita tandai `Expired`/`Failed`** (expire ke Midtrans 404 karena user belum memilih metode bayar). Uang harus tetap diterapkan atau ditampung, tidak diabaikan. Transisi di Task 2, cabang webhook di Task 5; dicek di Task 8 skenario 7.
4. **Webhook bersamaan dengan pembayaran manual admin** pada cicilan yang sama. Konflik `xmin` harus menjadi 503 (Midtrans mengirim ulang), dan percobaan berikutnya berakhir `Unapplied(InstallmentAlreadyPaid)`, bukan 500 permanen atau hilang. Task 5 Step 3; dicek di Task 8 skenario 8.
5. **Midtrans membalas 404 dalam body dengan HTTP 200** (`"status_code": "404"`) untuk order yang belum ada di Core API. Client harus memperlakukannya sama dengan HTTP 404 (status → `null`, expire → sukses). Task 3 Step 2; dicek di Task 8 skenario 6.

| Method | Status awal yang sah | Efek |
|---|---|---|

- [ ] **Step 4: Konfigurasi EF**

`PaymentTransactionConfiguration`:
- tabel `PaymentTransactions`, `Id` `ValueGeneratedNever`;
- `OrderId` max `EfConstants.Length.Short`, required, unique;
- `Status` dan `RejectionReason` `HasConversion<string>()` max `Short`;
- `Amount` `decimal(18,2)`;
- `SnapToken`, `RedirectUrl`, `RefundReference`, `ResolutionNote`, `PaymentType`, `MidtransTransactionId` max `Long`;
- `RowVersion` sebagai `xmin`, sama dengan `InstallmentConfiguration`;
- FK `InstallmentId` → `Installments`, `PremiId` → `Premis`, `AllocatedInstallmentId` → `Installments` (nullable), semuanya `DeleteBehavior.Restrict`, tanpa navigation;
- index `(PremiId, Status)`;
- unique index `InstallmentId` dengan filter `"\"Status\" = 'Pending'"`;
- index `ExpiresAt` dengan filter yang sama;
- `CreatedAt`/`UpdatedAt` default `CURRENT_TIMESTAMP`.

Tambah `PaymentTransactionIdConverter`, daftarkan di `ConfigureConventions`, dan tambah `DbSet` di context + interface.

Catatan: FK `Restrict` ke `Installments` membuat `Premi.Update` gagal di database jika cicilan lama sudah punya transaksi (cicilan lama dihapus saat jadwal dibuat ulang). Ini diterima, karena riwayat pembayaran tidak boleh hilang. Di handler `UpdatePremi`, tambah `catch (DbUpdateException ex) when (ex is not DbUpdateConcurrencyException)` → `Failure("Premi cannot be changed because payment links have been created.")`. File: `Chakra.Application/Features/Premi/Command/UpdatePremi.cs`.

### Task 5: Webhook notifikasi

**Files:**
- Modify: `Chakra.Application/Common/Response.cs`, `Chakra.API/Endpoints/ResultHttpExtensions.cs`

- Create: `Chakra.API/Endpoints/MidtransEndpoint.cs`

**Interfaces:**
- Consumes: `IMidtransClient.GetStatusAsync`, `MidtransNotificationDto` (Task 3); `PaymentTransaction.*`, `Premi.CheckCanPay`, `Premi.MarkInstallmentPaid` (Task 2).
- Produces:
  - `ErrorType.Unavailable` (ditambah di akhir enum) + `Result<T>.Unavailable(string)`; `ToErrorResult` memetakannya ke 503
  - `record ProcessMidtransNotificationCommand(MidtransNotificationDto Notification) : IRequest<Result<string>>`
  - `POST /api/midtrans/notification` (anonymous), nama `"Midtrans Notification"`

- [ ] **Step 1: Verifikasi signature**

`SHA512(order_id + status_code + gross_amount + ServerKey)` → hex lowercase, dibandingkan dengan `signature_key` memakai `CryptographicOperations.FixedTimeEquals`. Semua string dipakai **apa adanya dari body**. `ServerKey` kosong atau field null → tolak. Gagal → `Unauthorized("Invalid signature.")`.

- [ ] **Step 2: Konfirmasi status dan cari transaksi**

`GetStatusAsync(order_id)` melempar exception → log warning, `Unavailable("Payment status could not be confirmed.")`. Hasil `null` atau transaksi tidak ditemukan → log warning, `Success("Ignored.")`. Semua langkah berikutnya memakai `MidtransStatus`, bukan body notifikasi.

- [ ] **Step 3: Cabang status**

Ikuti tabel di spec bagian 3 (Webhook) langkah 4 dan "Penerapan Pembayaran", dengan rincian berikut:
- Settlement: `transaction.IsFinal` → `Success("Already processed.")`. `gross_amount` diparse dengan `decimal.Parse(value, NumberStyles.Number, CultureInfo.InvariantCulture)`. `settledAt` = `SettlementTimeUtc ?? now`.
- `CheckCanPay` tidak null → `MarkUnapplied(alasan, ...)`. Premi tidak ditemukan → `MarkUnapplied(PremiNotActive, ...)`.
- `refund`: `Status == Unapplied` → `MarkRefunded("midtrans", null, now, null)`.
- `SaveChangesAsync`. `DbUpdateConcurrencyException` → `Unavailable("Payment is being modified, please retry.")`. Exception lain dibiarkan naik (500).

- [ ] **Step 4: Endpoint**
